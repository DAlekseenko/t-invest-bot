# Открытые вопросы перед live

Разработка каркаса, read-only интеграций, sandbox и dry-run может начинаться сразу. Следующие решения блокируют только реальную торговлю.

## Q1. Что именно можно продавать

Текущая таблица рассчитывает `Продать, шт` относительно всей позиции. На отдельных глубоких уровнях количество может задействовать бумаги, купленные до запуска робота.

Варианты:

1. `ladder_only` — продавать только net-количество, купленное текущим циклом.
2. `entire_position` — разрешить продажу исходной позиции в пределах таблицы.
3. `protected_qty` — защищать явно заданное количество, остальное доступно стратегии.

Безопасное значение MVP: `ladder_only` с protected base SBER 58, TRNFP 28, BTBR 142.

Нужно решить, что делать, если `preview_sell_qty` больше доступного ladder inventory:

- блокировать выход как ошибку конфигурации;
- уменьшать до доступного количества;
- разрешать использование части base position.

Рекомендация для MVP: блокировать на этапе публикации, чтобы расхождение было видно заранее.

## Q2. Где живут формулы

Варианты:

1. Таблица рассчитывает готовые цены/количество, Go только валидирует.
2. Таблица хранит входные параметры, Go выполняет основной расчёт.
3. Формулы дублируются, а расхождение блокирует публикацию.

Рекомендация: вариант 3 на переходный период, затем вариант 2. Это позволяет сохранить знакомый preview и одновременно получить тестируемую доменную логику.

## Q3. Размещение BUY-заявок

Варианты:

1. Сразу выставлять все уровни как DAY limit orders.
2. Следить за ценой и создавать заявку только при достижении уровня.

Рекомендация: вариант 1. Текущий `Макс. резерв` уже описывает резерв под все уровни, а заявка находится у брокера при кратковременной недоступности сервера. Минус — блокируется весь резерв.

## Q4. Новый цикл

Варианты:

1. После выхода ждать новой ручной публикации.
2. Автоматически строить новую лесенку от цены выхода/рынка.

Рекомендация MVP: вариант 1 (`auto_restart=false`). Правила нового старта пока не формализованы.

## Q5. Частичное исполнение SELL

Нужно определить минимальное количество, после которого выход считается завершённым. Рекомендация MVP: цикл закрыт только после исполнения целевого количества; остаток менее одного лота невозможен по модели.

## Q6. Ручные операции в брокерском приложении

Нужно выбрать политику:

- полный запрет ручных операций по SBER/TRNFP/BTBR во время активного цикла;
- разрешение с автоматическим reconciliation;
- отдельный брокерский счёт для робота.

Рекомендация: отдельный счёт для робота либо запрет ручных операций по активным инструментам. Неизвестная заявка по тому же инструменту должна ставить стратегию на паузу.

## Q7. Комиссии и налоги

Нужно определить, входит ли комиссия в целевую доходность выхода. Рекомендация: Strategy Engine считает gross и estimated net P/L, но цена выхода формируется по net-target с комиссионным буфером. Налоги в торговое решение MVP не включаются, но сохраняются для отчётности при наличии данных.

## Q8. Канал уведомлений

Выбрать один канал для MVP:

- Telegram bot;
- email;
- только Grafana/Alertmanager.

Минимальные события: mode change, snapshot accepted/rejected, order placed/filled/rejected/unknown, reconciliation mismatch, cycle closed.

## Q9. Server constraints

Перед развёртыванием проверить на выбранном сервере:

- свободную RAM/CPU рядом с VPN;
- доступность T‑Invest gRPC endpoints;
- исходящий доступ к Google API;
- стабильность NTP;
- резервное копирование за пределы сервера.

## Decision checklist

```text
[ ] Q1 sell scope и поведение при превышении sell qty
[ ] Q2 источник формул
[ ] Q3 все BUY сразу или price trigger
[ ] Q4 auto restart
[ ] Q5 partial SELL completion
[ ] Q6 политика ручных операций/отдельный счёт
[ ] Q7 комиссия в target P/L
[ ] Q8 уведомления
[ ] Q9 сервер проверен
```
